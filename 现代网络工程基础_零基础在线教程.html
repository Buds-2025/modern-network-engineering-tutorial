学完并做完练习，你要能办成哪些事

目标是独立处理常见的小型网络任务：认出光猫、路由器和AP；查出自己设备的IP、网关和DNS；读懂一个简单子网；把本地网页跑起来；区分地址、名字、端口和应用故障；为家庭或小办公室画出基本连接与访问方案。容器和云网络部分让你能读懂常见配置，知道该从哪里检查。

这些能力要靠“读懂＋动手＋解释结果”一起建立。先不要求你配置运营商BGP、大型园区冗余或复杂生产集群；相关课程先帮助你看懂它们与日常通信的关系。遇到超出范围的问题，能准确描述现象和收集证据，也是一项工程能力。

  1. 第1～4课：认路。从盒子、网线和Wi-Fi开始，认出IP、子网、网关、MAC之间的分工。
  2. 第5～10课：让服务说上话。理解端口、NAT、DNS和HTTPS，知道服务为什么只能本机访问。
  3. 第11～16课：看懂现代环境。判断无线和性能问题，理解代理、容器、云网络与互联网路由。
  4. 第17～18课：独立完成。按证据排错，完成综合实操，再用验收表检查自己。

第1课　先看懂你身边的网络

你现在看到网页，背后至少经历了“设备接入→获取网络配置→解析域名→选择路径→连接服务器→交换数据”这一串动作。

1.1 家庭网络里到底有哪些设备

最常见的家庭结构是：运营商的光纤进入光猫，光猫把信号交给路由器，路由器再通过网线或Wi-Fi连接电脑、手机、电视、NAS等设备。有些运营商把“光猫＋路由器＋Wi-Fi”做成一体机，因此你看到的盒子可能比图里少。

光猫（ONT/ONU）主要负责接入运营商光纤网络。部分设备还集成拨号、NAT、DHCP、Wi-Fi。
路由器把不同网络连接起来。家庭里最常见的是连接“运营商一侧”和“家庭内网一侧”。
交换机主要连接同一局域网里的多台有线设备。它更关心MAC地址，而不是互联网路由。
无线AP让无线设备接入局域网。家用“无线路由器”通常把路由器、交换机、AP做在一个盒子里。

把家用网络想成一个小办公室：交换机把几张办公桌接在一起，AP让手机不用插网线也能加入，路由器负责通往外部网络。一个盒子能兼任好几项工作，所以认设备时，重点看它连接哪两侧、承担什么功能，别只看外壳上的名字。LAN通常是家里这一侧，WAN通常是通向上游网络的一侧。

“接口”是设备收发网络数据的接入口，可以是有线网口、无线网卡，也可以是软件创建的虚拟接口。“协议”是双方共同遵守的通信规则。电脑会把应用数据拆分、封装成较小的传输单位，IP这一层称为“数据包”，以太网这一层称为“帧”。像货物装进箱子再贴上运输标签，每一层增加自己需要的信息；这里先认名字，后面逐层看它们怎样配合。

1.2 公网、内网、局域网、互联网

内网是一个组织自己控制的网络，例如你家的192.168.1.0/24、公司的办公网。公网通常指全球互联网中可被全局路由的地址空间和网络。互联网则是大量独立网络互相连接形成的“网络之网”。

不要把“Wi-Fi”和“互联网”画等号。Wi-Fi只是一种局域网接入方式。你可以连上Wi-Fi却没有互联网；也可以完全不用Wi-Fi，通过网线、5G或光纤上网。

1.3 一台电脑上网前需要知道什么

以家庭IPv4网络通过域名访问网站为例，通常需要下面四类配置：

表1-1　一台电脑上网前需要知道什么
信息例子作用
IP地址192.168.1.23我是谁、别人怎样找到我
子网前缀/掩码/24 或 255.255.255.0哪些地址和我在同一网段

家庭IPv4网络通常通过DHCP自动取得这些配置。首次获取租约常经历Discover（发现）、Offer（提供）、Request（请求）、ACK（确认）四步，简称DORA；续租不必重新走完整四步。IPv6的配置机制有所不同，见第2课。

DHCP像接待处发放临时座位和出门路线：电脑说“我刚来，需要一套配置”，服务器给出可用地址，电脑确认使用，服务器记录租约。租约就是“这套地址可以用到什么时候”。同一网络里如果两台设备手动写了同一个IP，就像两个人拿到同一个座位号，通信可能时好时坏。

1.4 互联网为什么能把全球网络接起来

互联网不是一台超级交换机，也没有一个“总路由器”。它由运营商、云厂商、学校、企业、内容网络等大量自治网络组成。这些网络内部自己决定怎么路由，网络与网络之间再通过BGP交换“哪些IP前缀应该往哪里走”的信息。第16课会把这件事讲清楚。

小测：手机显示Wi-Fi满格，但网页打不开。能说明什么？
满格通常只反映收到的无线信号较强，不能证明干扰、竞争、丢包、AP回程、DNS或互联网出口正常。

1.5 动手：画出你家的网络

先不用打开路由器设置。观察网线和设备标签，画出“入户线路→光猫→路由器→电脑/手机”。如果一台盒子兼任多种功能，就在旁边分别写下。笔记本接Wi-Fi时，也请找出Wi-Fi后面通过什么设备连向运营商。

再回答三个问题：哪一段是无线？路由器的WAN口接向哪里？如果运营商线路暂时断开，手机和家里的网络打印机还可能互相通信吗？在没有客户端隔离等限制时，本地通信仍可能正常，因为它不一定经过互联网出口。

完成标志：能对着自己的图，指出本地连接和外网出口。认不出的设备先记型号和接线，别为补全图而拔线或重置。

本课核查依据：RFC 2131：DHCP。

第2课　IP地址：先搞懂“你在哪里”

IP地址不是设备的“身份证号”，更像某个网络接口在某个网络环境里的“邮寄地址”。同一台电脑可以同时有多个IP，换网络后IP也可能变化。

2.1 IPv4长什么样

IPv4地址是32位二进制数，通常写成四个0～255的十进制数，例如：

192.168.1.23
11000000.10101000.00000001.00010111

人类习惯看第一行，机器处理的是第二行所代表的比特。

一个比特只有0和1两种取值，8个比特合成一组，能表示256种组合，所以每组写成0～255。现在不用背二进制换算；先学会识别四段数字，检查有没有超过255的数。192.168.1.300就不是合法的IPv4写法。

2.2 公网IP与私有IP

RFC 1918保留了三段IPv4地址给私有网络使用：

表2-1　公网IP与私有IP
私有地址块常见场景
10.0.0.0/8企业、云VPC、大型内网
172.16.0.0/12企业、容器、实验环境
192.168.0.0/16家庭、小型办公室

这些地址不会在全球互联网中直接路由，所以你家和邻居家都可以有一台192.168.1.10。两个独立网络可以重复使用这些地址；通过VPN或专线互联时，重叠地址也会造成路由歧义，需要重新规划地址或实施转换。

私有IP有点像各家公司的内部分机号：A公司的“分机23”和B公司的“分机23”可以同时存在，打通两家公司后就要说清楚是哪一个。这个比方只说明地址可以在独立网络重复使用；真实通信还要看子网、路由和访问规则。

2.3 127.0.0.1和0.0.0.0

127.0.0.1：回环属于127.0.0.0/8回环地址块。访问它是在访问“本机自己”，数据不会被正常转发到外部网络。

2.5 动态IP为什么会变

普通家庭网络里，至少可能有两套“动态分配”：

公网地址是否会变，取决于运营商的接入与地址分配策略。重拨、租约更新、线路迁移、设备更换或运营商维护都可能导致变化；也可能几个月都不变。“动态”表示没有固定承诺，不表示必须定期变化。

公网IPv4地址数量有限，而联网设备越来越多。IPv6把地址长度从32位扩到128位，可以安排大得多的地址空间。IPv4和IPv6像两套不同的地址格式；设备同时支持两套称为“双栈”。它们常并存，不要求你先关掉其中一套才能上网。

2.6 IPv6：128位地址时代

IPv6把地址长度从32位扩大到128位。例如：

2001:db8:1234:5678::20

2001:db8::/32专门用于文档示例，真实部署不要照抄。IPv6的地址空间极大，设计上不依赖IPv4时代那种“大量终端共享一个公网IPv4”的NAT模式。IPv6仍然需要防火墙：可全球路由，不等于应该允许全球主动访问。

IPv6配置不只靠DHCP。主机可依据路由器通告（RA）获得前缀并通过SLAAC生成地址，也可使用DHCPv6分配地址或提供其他参数；默认路由通常由RA告知。现代客户端经常同时拥有IPv4和IPv6。当一个域名同时返回A和AAAA记录时，客户端可以根据网络可用性和性能选择连接路径；“Happy Eyeballs”类算法就是为减少双栈环境中的等待而设计。

小测：两台不相连的家庭路由器都给电脑分配192.168.1.23，会立刻冲突吗？
不会因为地址相同就跨家冲突。私有地址能在独立网络重复使用；把这些网络通过VPN等方式互联后，需要处理地址重叠。

第3课　子网、网关与路由：数据到底往哪走

“我知道目标IP了”还不够。设备还要判断：目标是不是和我在同一网段？如果不是，我该把包交给哪个下一跳？

3.1 192.168.1.0/24是什么意思

/24表示前24位是网络前缀，剩下8位用于区分该网段里的地址。对IPv4来说，一个/24覆盖256个地址，从192.168.1.0到192.168.1.255。传统子网语义下，网络地址和广播地址通常不分给普通主机，因此常见可用主机地址是.1到.254。

子网掩码255.255.255.0和前缀长度/24表达的是同一件事，只是写法不同。

把/24读成“前24位用于识别网络”。IPv4总共32位，剩下8位用于区分这一网段里的地址，因此共有2的8次方，也就是256个地址。常见普通/24子网会留出网络地址和广播地址，可分配给接口的通常是254个。斜杠后数字越大，地址块越小。

3.2 同网段时怎么走

电脑A：192.168.1.20/24，电脑B：192.168.1.80/24。在没有更具体路由或特殊策略、且两台设备处于同一二层网络的常见情形下，A根据直连路由向B发送：若邻居缓存没有可用条目，就先用ARP查询B的MAC地址，再在局域网内传输。

3.3 不同网段时怎么走

电脑A要访问8.8.8.8。显然它不在192.168.1.0/24，于是A查询路由表，通常匹配默认路由：

意思是：没有更具体规则时，下一跳交给192.168.1.1。这里的0.0.0.0/0表示覆盖全部IPv4目的地址的默认前缀。

第4课　MAC、ARP与局域网：IP下面还有一层

IP告诉你“逻辑上要去哪里”，而在以太网局域网中，真正把一帧数据交给本地下一跳时，还要用到链路层地址。

4.1 MAC地址是什么

以太网接口通常有一个链路层地址，常写成：

3C:52:82:AB:10:7F

它和IP不是同一个层次。IP可以随网络变化；MAC通常由接口/软件配置决定，现代操作系统也可能为隐私使用随机化MAC，因此不要把它理解成“永不变化的硬件身份证”。

沿用投递的比方：IP说明最终要到哪个网络地址，MAC帮助数据在当前这段局域网里交给下一台设备。经过路由器进入下一段以太网时，会重新封装链路层帧，源、目的MAC通常随这一跳改变。MAC只解决本地这一段的交付，不能拿一个远方网站的MAC直接横跨互联网找它。

4.2 ARP解决什么问题

假设A知道下一跳IP是192.168.1.1，但以太网帧还需要目的MAC。ARP的工作就是在本地IPv4网络里问：

图4-1　ARP：知道IP，寻找本地链路地址
A谁是192.168.1.1？
⇒
局域网广播
⇒
网关192.168.1.1是我，MAC=…

得到结果后，操作系统会缓存一段时间，避免每个包都重新询问。

ARP像在同一房间里问：“谁是192.168.1.1？请告诉我你的MAC。”请求通常广播出去，拥有这个IPv4地址的设备回答，电脑把结果暂存下来。广播的意思是在当前广播域内向大家发送，普通路由器不会把这种ARP询问原样转到全球网络。缓存过期后还可能重新询问。

4.5 一次局域网访问到底发生了什么

  1. A查询路由表；这里假设B在同一二层网络，并匹配直连路由。
  2. 若邻居缓存没有B的可用条目，A通过ARP查询B的MAC。
  3. A封装以太网帧，目的MAC写B。
  4. 交换机查MAC地址表；已知目的MAC时转发到相应端口，未知单播则在该VLAN内向其他端口泛洪。
  5. B解封装，交给IP层，再交给TCP/UDP和应用。

第5课　TCP、UDP与端口：找到机器以后，还要找到程序

IP地址把数据送到某台主机，端口再帮助传输层把数据交给正确的应用。TCP与UDP则定义了“怎样运送”。

5.1 端口是什么

端口号是16位数字，范围0～65535。一个常见服务地址写成：

203.0.113.10:443

前半部分是IP，后半部分是端口。IANA把端口范围分为系统端口0～1023、用户端口1024～49151、动态/私有端口49152～65535。注意：端口号只是约定和标识，看到443不代表流量一定安全，看到8080也不代表一定是Web服务。

用办公楼作比方，IP是楼的地址，端口像接待窗口编号。但窗口号还要连同TCP或UDP一起看：53/TCP和53/UDP是不同的通信端点。浏览器、聊天工具能同时联网，是操作系统在依据地址、端口和协议把数据分给对应的连接与程序。

5.2 TCP：可靠、有序的字节流

TCP会建立连接，提供按序字节流，并处理确认、重传、流量控制等问题。先抓住三个动作：

图5-1　TCP三次握手（简化）
客户端SYN
→
服务器SYN + ACK
→
客户端ACK，连接建立

“可靠”不等于“永不丢包”。恰恰相反，网络可能丢包，TCP通过序号、确认、超时和重传把这种不可靠性尽量屏蔽给上层应用。

TCP有点像按页码寄一份材料：收到乱序的页先整理，少了一页设法补传，最后向应用交出连续的字节。TCP不知道哪些字节算“一条消息”，应用还要自己约定分隔方式。三次握手是双方先交换确认“彼此能收发、从哪个序号开始”的过程；它不负责核实网站身份，身份验证要看TLS等机制。

5.3 UDP：最小机制的数据报传输

UDP不建立类似TCP的可靠字节流连接，也不替应用保证重传和顺序。它提供的是较轻量的数据报接口。DNS传统查询、实时音视频、游戏，以及QUIC底层都可能使用UDP。

TCP更像“有签收和补发机制的物流”应用更容易得到可靠、有序的数据流，但协议状态和丢包恢复会带来额外机制。
UDP更像“直接发独立包裹”基础机制少，但上层协议可以自己决定要不要确认、重传、排序、加密。
不要背成“TCP慢、UDP快”。真实性能取决于协议设计、网络状况、实现、拥塞控制和应用需求。QUIC就是一个典型反例：它跑在UDP之上，却自己实现可靠传输、拥塞控制、多路流和安全机制。

UDP更像一次投递一张便条：保留这张便条的边界，但协议本身不承诺补发、排序或一定到达。应用可以按需要自己加上这些能力。语音通话有时宁可丢掉一小段旧声音，也不愿等很久再播放；文件下载则需要把内容补齐。选择哪种机制要看用途。

5.4 服务端端口与客户端临时端口

你访问HTTPS网站时，服务器通常监听443；客户端本地会临时选一个端口，例如：

客户端 192.168.1.23:53142  →  203.0.113.10:443

服务器回复时反过来：

203.0.113.10:443  →  192.168.1.23:53142

因此“访问443”不代表你的电脑只用443。客户端往往使用临时源端口去连接服务器的固定服务端口。

5.5 Socket可以怎么理解

在工程语境里，socket是操作系统提供给应用的网络通信接口。一个具体连接通常由协议和两端地址共同标识，例如TCP连接可以用“五元组”理解：

源IP + 源端口 + 目标IP + 目标端口 + 传输协议

第6课　NAT、端口映射与家庭上网

这一课解释两个常见的家庭上网问题。它解释了：为什么家里十几台设备可以共用一个IPv4上网，以及为什么你在家里开了服务器，外网却不一定能连进来。

6.1 NAT到底在改什么

NAT是地址转换的总称。家庭IPv4最常见的是带端口转换的NAT/PAT：许多私网地址通过不同端口映射到一个外部地址。

图6-1　多个家庭设备共享一个外部IPv4（简化）

192.168.1.11:52002手机
→
家庭路由器NAT/PAT表
→
198.51.100.20外部看到的地址

路由器会维护状态表，知道返回到某个外部端口的流量应该交给哪台内网设备。外部网站通常看不到你真实的192.168.1.x。

NAT/PAT像前台替几个人向外打电话，并记下一张转接表：“外面这个通话，对应里面哪台设备的哪个端口”。回复回来时按表转交。它主要解决地址转换；前台并不会自动知道，外面突然打来的一个新电话该找里面的谁。实际是否放行还由防火墙和连接跟踪等规则共同决定。

6.2 为什么“内网主动出去”容易，“公网主动进来”困难

当内网设备先发起连接时，NAT设备可以顺手建立映射状态；而一个陌生公网数据包突然到达路由器，如果没有已有状态或静态规则，路由器不知道该交给哪台内网设备。

6.3 端口映射是什么

端口映射（Port Forwarding）就是人为建立一条固定转发规则：

图6-2　外部端口 → 内部主机端口
公网IP:50000外部访问入口
→
路由器端口转发规则
→
192.168.1.50:80内网Web服务

公网端口和内网端口可以不同，例如公网50000映射到内网80。所谓“公网端口”，并不是一种新类型端口，只是“一个可从外部地址访问的端口位置”的口语说法。

6.4 公网IP会不会变

普通家庭宽带常使用动态地址：运营商可以在连接建立、租约更新、重拨或网络调整时重新分配。也可能长期维持同一地址，但只要合同没有承诺静态地址，就不该把它当永久不变。

如果要长期从外部访问一个动态公网IP，可以使用DDNS：域名记录随公网IP变化自动更新。它解决的是“地址变了以后名字还能找到它”，不解决CGNAT和防火墙问题。

6.5 CGNAT：你家路由器外面可能还有一层NAT

由于IPv4地址紧张，运营商可能让多个家庭再共享一个公网IPv4。RFC 6598专门保留100.64.0.0/10给运营商共享地址空间。

6.6 怎么初步判断自己是否在CGNAT后面

  1. 进入路由器查看WAN IPv4地址。
  2. 再从浏览器访问可信的“查看公网IP”服务。
  3. 比较同一出口路径上的IPv4地址。先关闭会改变出口的VPN或代理；若WAN地址与外部观察值仍不一致，很可能存在上游NAT，但不能只凭这一点断定运营商CGNAT。
  4. 如果WAN地址属于100.64.0.0/10，这是CGNAT的强信号；如果是10/8、172.16/12、192.168/16，也说明上游存在私网层。

6.7 内网穿透是什么

当外部无法直接主动连接内网时，可以让内网设备先主动连到一个公网可达的中继/协调服务，再通过反向隧道、P2P打洞或虚拟组网建立访问路径。不同产品实现差异很大，常见思路包括：

反向隧道内网端主动建立长期出站连接，由公网端转发请求。
NAT穿透借助STUN/ICE等探测与协商，尽量建立点对点路径；失败时可能需要TURN中继。
虚拟组网给设备创建一个加密覆盖网络，让分散设备像在同一私网中通信。
安全提醒：“能从公网访问”不是目标本身。开放端口前先问：服务是否需要直接暴露？是否有强认证？是否能限制来源IP？是否能放在VPN/零信任访问层后面？

6.8 先判断方向，再考虑端口映射

场景A：电脑主动打开网站。路由器通常为这次出站通信建立转换状态，让返回数据找到电脑。场景B：朋友从外面主动访问你家的相册服务。这是新的入站连接，需要明确的服务入口；常见家庭IPv4环境里可能涉及端口映射，还要检查公网地址、上游NAT和访问控制。两种方向不要混在一起。

DDNS像不断更新门牌地址的通讯录，只解决“地址变化后怎样找到”的问题，不能让运营商CGNAT自动替你开门。内网穿透通常借助设备主动连出的通道或中继，也仍然需要认证、权限与维护。

本课先做纸上检查：服务在哪台机器、监听哪个地址和端口、谁要访问、走IPv4还是IPv6、经过几层路由和防火墙。暂时不要把演示网页或数据库发布到公网。家庭公网入站测试应从真正的外部网络验证，在家里访问自家公网地址的结果还可能受NAT回流能力影响。

小测：IPv6设备有全球单播地址，就一定能从外网连进来吗？
不一定。地址可被全球路由与服务可达是两件事；运营商路径、路由器IPv6防火墙、主机防火墙和应用监听都可能限制入站。IPv6通常不依赖家庭IPv4式NAT，也仍需访问控制。

第7课　域名体系：给互联网地址起一个人类能记住的名字

域名不是服务器，也不是IP地址。它更像一个可管理、可解析的名字。真正把名字变成网络地址的工作，由DNS完成。

7.1 为什么需要域名

人类不擅长记住大量IP地址，而且服务器地址还可能变化。如果每个网站都要求用户背203.0.113.25这样的数字，互联网几乎无法正常使用。因此我们用example.com这样的名字，再让DNS去查它当前对应什么。

7.2 域名是分层的

域名从右往左看层级：

例如：

这完全正常。注册商管理“这个域名由谁注册”；Nameserver告诉互联网“这个域名的权威DNS去哪里问”；DNS记录再告诉客户端“具体服务去哪个IP或名字”。

7.6 Nameserver是什么

当域名example.com的NS被设置为某组权威DNS服务器时，相当于告诉DNS体系：

“关于example.com下面的权威答案，请去问这些服务器。”

因此把DNS托管从A迁到B，常常需要在注册商处更新Nameserver。只是修改某条A记录，则通常只需在当前DNS托管商处操作。

可以把域名当成店名，把DNS记录当成“店目前在哪个地址”的指引，把服务器当成真正提供服务的场所。店名续费、改地址、搬服务，是三项不同的操作。只注册域名不会自动出现网页；只改DNS也不会自动安装Web服务或申请好证书。

7.7 域名、端口与URL别混

拆开下面这个地址：

https://api.example.com:8443/v1/users?id=12
└https  协议
        └api.example.com  主机名
                        └8443  端口
                             └/v1/users  路径
                                       └?id=12  查询参数

https://example.com没写端口时，客户端会按HTTPS URI语义使用默认443；http://example.com默认80。端口仍然存在，只是URL里省略了。

7.8 为什么example.com和www.example.com可以不同

它们是两个不同的DNS名称。站长可以把它们配置到同一服务，也可以完全不同。很多网站把一个重定向到另一个，是网站策略，不是DNS天然保证。

7.9 域名与HTTPS证书

TLS证书会声明它对哪些DNS名称有效。例如证书可覆盖example.com，也可覆盖*.example.com这样的通配符范围。浏览器访问某个主机名时，会验证证书中的名称是否匹配。通配符*.example.com通常只覆盖一级子域，如www.example.com，不覆盖example.com或a.b.example.com。直接用IP访问仅包含域名身份的证书，通常会名称不匹配；IP访问需要相应的IP地址身份。

7.10 国内网站备案要和域名注册分开理解

如果教程面向中国大陆部署场景，要把“注册域名、购买服务器、DNS解析、ICP备案/许可”等事情分开。它们是不同环节，适用要求会随服务性质、主体、服务器所在地和监管政策变化。实际发布前应以工信部及接入服务商最新官方规则为准。

7.11 拆一条网址，不急着购买域名

在纸上拆开https://docs.example.com:8443/start?lang=zh#install：HTTPS是协议，docs.example.com是主机名，8443是端口，/start是路径，lang=zh是查询参数，#install是片段，通常交给浏览器定位或前端处理，不随普通HTTP请求目标发送给服务器。域名里不包含https://、端口和后面的路径。

如果迁移一个网站，先列出三项：新服务入口、DNS记录、HTTPS证书。DNS已经改对，但新服务器没有该站点配置或有效证书，网页仍可能失败。这能解释为什么“域名解析成功”和“网站迁移完成”不能画等号。

小测：持有*.example.com的证书，能直接覆盖example.com和a.b.example.com吗？
这个通配符通常只覆盖一个子域标签，例如docs.example.com。裸域名example.com和两级子域a.b.example.com都需要证书中另外合适的身份声明。

第8课　DNS：互联网怎样把名字变成答案

DNS常被比作互联网电话簿，但它比电话簿复杂：它是一个全球分布式、分层、带缓存的数据库系统。

8.1 一次DNS查询经过哪些角色

当你访问www.example.com时，电脑上的“存根解析器”通常把问题交给递归DNS解析器。递归解析器如果没有缓存，会沿DNS层级寻找答案。

查地址时，你通常只问一个帮忙查找的服务台，这就是递归解析器。它去问总目录、分类目录，最后找到真正负责该名字的权威服务器。权威服务器像这家店维护的地址登记处；递归解析器像替你查资料并暂存结果的人。先分清“谁替我查”和“谁负责公布答案”，后面的DNS设置就容易读懂。

8.3 TTL为什么重要

DNS记录带有TTL，允许缓存一定时间。好处是降低延迟和权威DNS负载；代价是修改记录后，旧答案可能在缓存里继续存在一段时间。

“DNS多久生效”没有一个全球统一的倒计时。它取决于旧记录TTL、各层缓存、客户端行为以及你修改的是记录本身还是Nameserver委派。把“修改后几分钟全世界一定生效”当固定规则是不准确的。

假设某条记录的TTL为300秒，解析器刚拿到它，通常可以缓存最多300秒。你过100秒再查询，可能看见剩余TTL约200秒。这像给临时抄下来的地址贴上“多久后需要重查”的便签；它不意味着你改记录以后，全球所有缓存都会从新值开始重新计时。

8.4 DNS默认用UDP还是TCP

传统DNS查询大量使用UDP 53，但DNS也使用TCP 53，例如响应过大、区域传送等场景。完整的DNS实现需要支持TCP；收到被截断的UDP响应后，客户端通常会改用TCP重试。现代DNS还有加密传输：

DoTDNS over TLS。用TLS保护DNS客户端与解析器之间的查询通道。
DoHDNS over HTTPS。把DNS查询响应映射到HTTPS交换。

它们主要改善“传输通道的隐私和防篡改”。DNSSEC解决的是另一件事：通过签名帮助验证DNS数据来源与完整性；DNSSEC本身不提供查询内容的机密性。

8.5 为什么换DNS有时能“修网”

如果你的网络能访问IP，但域名打不开，可能是DNS解析环节异常。换递归解析器可能绕过故障或污染，但并不能修复所有网络问题。若路由、TLS、服务器本身有问题，换DNS不会神奇解决。

8.6 实训：查清一个域名

# Windows
nslookup example.com
nslookup -type=mx example.com

# Linux / macOS
dig example.com A
dig example.com AAAA
dig example.com NS
dig +trace example.com

dig +trace非常适合学习DNS层级，因为它能展示从根开始逐步找到权威答案的过程。

8.7 常见误区

域名解析到IP后，浏览器是不是直接访问这个IP就一定一样？

不一定。HTTP Host、TLS SNI、证书、CDN边缘路由、虚拟主机都可能依赖域名。只把域名替换成IP，可能得到不同站点或直接失败。

CNAME能不能想配在哪里就配在哪里？

传统DNS语义下，同一个名称如果是CNAME，通常不能再同时拥有其他普通数据。区域顶点还涉及特殊限制；一些DNS服务商提供“扁平化/ALIAS/ANAME”一类产品能力，但它不是普通CNAME语义。

8.8 动手：读懂一次DNS查询的结果

先运行nslookup example.com。通常顶部的Server/Address指你正在询问的DNS解析器，后面的名称与地址才是查询结果。别把“DNS服务器的IP”误认成“网站的IP”。看到“非权威应答”通常表示答案来自递归解析器，不代表答案一定错误。

# Windows、macOS及安装了nslookup的Linux
nslookup -type=A example.com
nslookup -type=AAAA example.com

分别记录A和AAAA的结果，再与本机DNS配置对照。某个名称没有AAAA可以是正常情况；查询超时表示在等待响应，NXDOMAIN表示解析器回答这个名称不存在，两者不是同一个症状。网络策略、解析器缓存和CDN调度可能导致不同设备看到不同答案，不要求你的地址与教程或他人的截图一样。

小测：DNS返回了一个IP，但浏览器仍打不开，接下来该查什么？
继续查实际访问的地址族、路由、传输端口、TLS和HTTP，不能只重复改DNS。浏览器还可能使用独立的安全DNS、缓存或代理，命令行的查询结果只是证据之一。

第9课　HTTP、HTTPS、HTTP/2、HTTP/3与QUIC

HTTP定义“Web客户端和服务器如何表达请求与响应”；TLS负责安全；TCP或QUIC负责把HTTP数据可靠地送过去。版本升级主要在效率、并发、延迟和部署方式上演进。

9.1 HTTP究竟是什么

HTTP是无状态的应用层请求/响应协议族。浏览器可以发送：

GET /docs HTTP/1.1
Host: example.com
Accept: text/html

服务器再返回状态码、响应头和内容。常见状态码：

表9-1　HTTP究竟是什么
范围含义例子
2xx成功200 OK
3xx重定向/缓存相关301、302、304
4xx客户端请求侧问题400、401、403、404、429
5xx服务器侧失败500、502、503、504

HTTP像一次有格式的点单：方法说明想做什么，路径说明要哪个资源，响应状态码说明处理结果。200常表示成功，404表示服务器没找到请求的资源，500表示服务器内部出错。收到404已经说明有HTTP响应回来，排查重点应转向网址路径和服务配置。

9.2 HTTPS是什么

HTTPS是通过安全传输保护HTTP语义。现代Web里通常使用TLS。TLS 1.3旨在防止窃听、篡改和消息伪造，并通过证书等机制帮助客户端认证服务器。

图9-1　不要把HTTPS和HTTP版本混为一谈
HTTPS“安全地使用HTTP”
可承载
HTTP/1.1
HTTP/2
HTTP/3

TLS像把通信装进能核对收件人身份、也能发现篡改的保护套。它保护传输过程，却不能保证网站内容诚实、下载文件无害。浏览器的安全连接提示不能替你判断陌生网站是否可信；证书名称不匹配也不应靠反复点击“继续”来处理。

9.3 HTTP/1.1、HTTP/2、HTTP/3的核心差别

图9-2　现代Web协议栈

HTTP/2
HTTP/2 → TLS（浏览器Web部署通常如此）→ TCP → IP

HTTP/2在一个连接中支持多个并发交换，并对字段进行压缩，提高网络资源利用率、降低延迟。问题在于：所有这些流仍共享同一条TCP字节流；如果TCP层缺少前面的字节，后续字节即使已经到达，也必须等缺失部分恢复后才能按序交给上层。

9.4 QUIC到底是什么

QUIC是IETF标准化的安全通用传输协议。它把QUIC包放在UDP数据报中传输，并提供：

多路流一个连接里有多个独立流，每个流有自己的有序字节序列。
低延迟建连传输参数与TLS握手紧密结合，可减少新连接等待；恢复已有会话且满足条件时可使用0-RTT，但早期数据存在重放风险，应用须限制可重放操作。
连接迁移通过Connection ID等机制，让客户端网络路径改变后仍有机会延续连接。
QUIC在UDP之上提供完整的传输机制。UDP只是它容易部署的承载层。可靠交付、确认、丢包恢复、流量控制、拥塞控制、多路流、安全握手等主要能力由QUIC自己提供。

“流”可以先理解为一条连接里相对独立的一路数据，例如一张图片一路、一个脚本一路。多路复用让它们共享连接交错传送，像在同一条运输线路上给货物贴不同的分组标签。HTTP/3把可靠传输等工作交给QUIC；底层用UDP，不代表网页资源可以随便缺字节。

9.5 为什么HTTP/3减少队头阻塞

假设HTTP/2的多个请求共享TCP连接，底层TCP某段数据丢失，后面的TCP字节即使属于另一个HTTP/2流，也无法越过缺口交付。QUIC的可靠性通常在独立流上体现：一个流的数据丢失，不要求其他流等待同一个字节序列缺口。

图9-3　直觉图：一个流丢包，其他流仍可前进
QUIC连接
→
Stream 1HTML ✓
Stream 2图片：有丢包
Stream 3API ✓

多个流仍共享连接级拥塞控制；流量控制或QPACK解码依赖也可能造成等待。减少传输层跨流队头阻塞，并不意味着HTTP/3在任何网络都更快。CPU、UDP策略、网络质量、连接复用、拥塞控制、服务器实现、路径中间设备都会影响结果。

9.6 HTTP/3为什么常见于UDP 443

IANA注册表中HTTPS同时登记了TCP 443和UDP 443。现实里，HTTP/1.1与HTTP/2通常跑在TCP 443；HTTP/3使用QUIC，通常使用UDP 443。服务器因此可以同时监听TCP 443和UDP 443，不冲突，因为传输协议不同。

9.7 浏览器怎么知道网站支持HTTP/3

现代部署可通过此前连接信息、HTTP响应中的Alt-Svc机制，以及DNS HTTPS/SVCB相关能力等途径发现替代服务。实现与浏览器策略会变化。对初学者来说，只需知道：URL仍然是https://，浏览器在背后协商或发现可用的HTTP版本。

第10课　防火墙与网络安全：能通信，不代表应该放行

现代网络工程的第一原则之一：减少不必要的暴露面。服务只开放给真正需要的来源、接口和身份。

10.1 防火墙在做什么

防火墙根据规则决定网络流量是否允许通过。规则可能考虑源/目的IP、端口、协议、连接状态、接口、应用甚至更高层信息。

防火墙像按名单检查访客的门禁：谁来、找哪个窗口、使用什么协议，都可以成为条件。程序监听像窗口有人值班，规则放行像允许进入走廊，账号验证像办业务前核实身份。三个环节各有作用，只开其中一个不等于其他环节就已正常。

10.3 127.0.0.1为什么常用于“只给本机”

如果数据库管理接口只供同一台服务器上的应用使用，可以绑定127.0.0.1。这样即使网卡有公网地址，服务也没有在外部接口上监听。相比“监听所有接口后再靠防火墙挡住”，这是更小的暴露面。

10.4 0.0.0.0为什么要谨慎

很多服务器框架中0.0.0.0表示绑定全部IPv4接口。如果机器同时有内网和公网接口，这可能让服务在你没有意识到的网络上出现。容器平台、云安全组和宿主机防火墙还会进一步决定是否可达。

10.5 入站与出站

家庭路由器和云安全策略常区分入站和出站。普通客户端通常需要主动出站访问互联网；服务器则可能需要允许特定入站服务。企业网络还会限制出站，防止恶意软件或数据外传。

10.6 最小暴露的实用清单

  1. 不需要公网访问的服务，绑定回环或内网地址。
  2. 数据库、Redis、管理后台不要默认裸露公网。
  3. SSH优先密钥认证，限制来源，禁用弱口令。
  4. 云安全组只开放必要端口和来源。
  5. 对管理面优先使用VPN/零信任访问层，而不是直接暴露。
  6. 及时更新软件，开启日志和失败登录监控。
端口换成高位随机数不是安全机制。它可能减少一些自动扫描噪声，但服务仍然可能被发现。真正安全来自认证、加密、访问控制、补丁、隔离和最小权限。

10.7 练一遍：把“放行”写成一条明确需求

“把8000打开”还不够明确。完整需求应写成：“允许家庭局域网中指定测试电脑，以TCP访问我的实验机8000端口；实验后撤销临时规则。”来源、目标、协议、端口和用途写清楚，才知道该改哪一道门。0.0.0.0/0作为IPv4来源范围表示所有IPv4来源，不应为了省事直接用于管理服务。

如果本机能打开实验网页，另一台设备打不开，先看监听地址，再确认两台设备是否同网、是否有访客隔离，随后检查对应的防火墙规则。确需建立规则时，用系统官方界面只允许必要的程序或端口，并限定实际来源和网络配置文件；不要把整个防火墙关掉。

小测：Web程序换到一个很少见的端口，还需要登录和补丁吗？
仍然需要。端口号可以被发现，改号无法替代身份验证、访问控制、加密和软件更新。
完成标志：能写出一条有来源、有协议、有端口、有用途的访问需求，并说明实验结束后如何撤销。

第11课　Wi-Fi与家庭网络：信号满格为什么还会卡

Wi-Fi只是“设备到无线接入点”的一段链路。网页加载速度还取决于路由器、运营商、DNS、远端服务器和整个路径。

11.1 2.4GHz、5GHz、6GHz先怎么理解

2.4GHz覆盖和穿墙通常更有优势，但可用频谱少、干扰常更多。
5GHz现代家庭主力频段之一，通常有更多可用信道和更高容量，覆盖受环境影响。
6GHzWi-Fi 6E扩展到6GHz，Wi-Fi 7也可使用该频段；频谱可用范围由当地法规决定，并非所有Wi-Fi 7设备都支持6GHz。

这些是经验方向，不是绝对规律。墙体材料、距离、天线、发射功率、法规、邻居网络和终端能力都会改变结果。

11.2 Wi-Fi信道与频宽

无线网络共享空气。邻居AP和你使用相同/重叠信道，就像多人同时抢一条单车道。更宽的信道可以提高峰值吞吐，但也更容易受到干扰和频谱条件限制。

11.3 Wi-Fi 6、6E、7主要提升什么

入门时可以先关注：多设备并发效率、频谱利用率、峰值速率、延迟控制等。Wi-Fi 6主要对应802.11ax；6E把相关能力扩展到6GHz；Wi-Fi 7对应802.11be，支持MLO、4096-QAM等能力，320MHz信道用于允许的6GHz频谱。实际收益取决于AP、终端、地区法规、干扰与回程。

“回程”就是AP或Mesh节点把数据送回主路由器的那段路。手机到卧室节点只有两米，卧室节点到主路由器却要穿三堵墙，这段回程就可能拖慢全程。“漫游”是手机移动时切换到另一个接入点；同一个Wi-Fi名字并不保证切换瞬间永远无卡顿，终端也参与决定。

11.4 Mesh是什么

Mesh系统通过多个节点扩大覆盖，并统一管理SSID、漫游和回程路径。关键是：

Mesh不能创造不存在的带宽。如果卫星节点到主节点的无线回程很差，终端连上卫星即使信号满格，整体速度仍可能很低。能做有线回程时，通常更稳定。

11.6 家庭网络优化顺序

  1. 先有线直连测速，确认运营商线路和出口能力。
  2. 再测路由器附近Wi-Fi，排除终端问题。
  3. 再到问题房间测信号、吞吐、延迟和丢包。
  4. 优化AP位置、信道和回程；必要时增加AP，而不是一味提高发射功率。
  5. 把固定高带宽设备尽量用网线接入。

11.7 动手：用三个位置找出无线瓶颈

在网络空闲时，使用同一台电脑，依次记录：有线接路由器、在路由器附近连Wi-Fi、在原来卡顿的房间连Wi-Fi。没有网口可以先比较后两个位置，并记下少了有线基准。每次用同一个测试目标，记录连接方式、频段、网关RTT、下载结果和是否卡顿，换位置后确认没有误连到另一个热点。

近处正常、远处明显变差，优先检查覆盖、墙体、干扰和回程；有线和无线都慢，优先检查共同经过的出口、上游和远端服务。这个对照能缩小范围，不能凭一次结果立刻认定设备损坏。重复几次、排除后台上传后再决定移动AP或调整配置。

买新路由器前先试两件小事：把设备移出封闭柜体，尽量放在覆盖区域中央；固定电脑、电视等能接网线的设备优先用网线。频宽调到最大未必最好，在拥挤环境里较窄信道可能更稳定，要用同样的方法复测。

第12课　网络性能：带宽大，不等于体验一定快

网络体验至少要同时看带宽、延迟、丢包、抖动和协议行为。单看“千兆宽带”很容易误判。

12.1 Mbps和MB/s差8倍

运营商带宽通常用bit/s；下载软件常用Byte/s。1 Byte = 8 bits，所以理想情况下：

1000 Mbps ÷ 8 ≈ 125 MB/s

真实下载还要扣除协议开销，并受服务器、磁盘、Wi-Fi、TCP/QUIC拥塞控制等影响，因此达不到125MB/s很正常。

12.2 延迟、RTT、抖动、丢包

带宽像一段路每秒能通过多少货，延迟像一趟往返要花多久，抖动像每趟所用时间忽长忽短。宽路可以多装货，却不会自动让很远的两地变近。看视频下载关注持续吞吐，视频会议还要关注延迟、抖动和丢包；这些指标不能互相替代。

12.3 为什么跨洲网站“带宽够但还是慢”

光在光纤中的传播也需要时间，跨洲路径还会经过多跳路由。一个应用如果需要多轮握手和串行请求，几十到几百毫秒RTT会被反复放大。所以现代协议一直在减少往返次数、复用连接、并行传输。

12.4 丢包为什么会拖慢可靠传输

TCP和QUIC都需要拥塞控制，不能发现丢包还无限加速。丢包可能触发重传和降低发送速率。如果Wi-Fi干扰严重、链路拥塞或路径质量差，即使套餐带宽很高，实际吞吐也会下降。

12.5 Bufferbloat：速度快但延迟突然爆炸

如果网络设备排队缓存过大，当上行或下行被跑满时，实时小包可能要在巨大队列后面等待，于是延迟从几十毫秒飙到几百甚至上千毫秒。表现就是：测速很快，但一有人上传/下载，视频会议和游戏立刻卡。

12.6 CDN为什么能加速

CDN把可缓存内容或代理入口放到更靠近用户的位置，减少网络距离，并利用更好的骨干和边缘调度。

12.8 练一遍：速度、等待时间分开算

100Mbps换算成十进制单位，理论约为12.5MB/s。下载一个100MB文件，单看带宽，传输时间下限约为8秒；还没算握手、协议开销和服务端等待。下载软件若显示MiB/s，使用的是另一种二进制单位，不能只看数字就直接比较。

再假设某个操作必须串行完成5次往返，每次RTT为100毫秒，仅往返等待就约需500毫秒。带宽从100Mbps升级到1000Mbps，也不会直接抹掉这500毫秒。这里是假设条件下的计算，用来说明等待与传输是两笔时间。

做性能记录时至少分三栏：空闲时的RTT、网络忙时的RTT、持续吞吐。若上传一开始，延迟就明显升高，停止上传后恢复，可以怀疑拥塞排队或Bufferbloat；还需结合链路和设备情况确认。不要用正在进行的测速干扰重要会议，也不要把一次ping超时就算成实际业务丢包率。

小测：一跳traceroute显示很多星号，但网页一直正常，需要立刻认定那台路由器坏了吗？
不需要。中间设备可以不回应或限速探测，却正常转发业务。结合后续跳、终点和实际应用表现判断；探测响应与正常数据转发是不同的观察对象。

13.5 TUN模式到底是什么

TUN通常是操作系统提供的虚拟三层网络接口。代理软件使用TUN时，可以让系统把IP数据包送进这个虚拟网卡，再由代理程序决定怎么转发。这样即使应用本身不支持“设置代理”，它的流量也可能被接管。

这解释了一个常见现象：某些软件在“系统代理”模式下不走代理，因为它根本不读取系统代理设置；打开TUN后却能工作，因为它看到的是操作系统路由层面的虚拟网络。

“隧道”可以理解为把原来的数据包再装进一层外包装，先送到隧道另一端，再拆开继续转发。它并不凭空缩短物理距离，还会增加一些协议开销。TUN则像操作系统里的一个虚拟收发口，程序从这个接口接走IP包，再决定怎样封装和转发。

13.7 WireGuard为什么常被提到

WireGuard是一种现代VPN协议/实现，使用公私钥配置peer，并通过虚拟网络接口和AllowedIPs等概念决定哪些地址经隧道发送。它的配置模型相对小，但真正部署仍需理解路由、NAT、防火墙和密钥管理。

13.8 分流：不是所有流量都必须进隧道

常见两种模式：

全隧道 Full Tunnel默认路由也指向VPN，绝大多数流量经隧道。
分流 Split Tunnel只有特定网段或目标走VPN，其他流量直接上网。
VPN不是“自动匿名器”。它只是改变了信任和流量出口：本地网络看到的内容减少了，但VPN服务端可能看到更多元数据。HTTPS等端到端安全仍然重要。

13.9 动手：给“流量绕路”画两条线

只查看自己的系统代理、浏览器代理和VPN设置，先不改动企业管理配置。在笔记里分别画出“浏览器→代理→网站”和“电脑→VPN网关→目标网络”。前一条可能只影响遵循代理设置的应用，后一条影响哪些目标，要看路由和分流规则。

如果VPN只给10.20.0.0/16配置了隧道路由，访问公司10.20网段会进入隧道，其他互联网流量在没有更匹配规则的常见情况下仍走原出口。若默认路由也进入VPN，大量互联网流量就可能跟着绕行；具体还要核对策略路由、IPv6和DNS。

小测：开着代理时浏览器能访问，命令行工具却失败，能证明电脑完全断网吗？
不能。两者可能走不同代理设置、DNS和网络路径。先记录各自配置与错误，确认是否经过同一个出口，再比较结果。不要把某一个应用的成功或失败直接推广到全部程序。

第14课　Docker与容器网络：为什么容器里的127.0.0.1不是宿主机

容器最容易让网络新手困惑，因为“同一台物理/虚拟机器”里突然出现了多个网络命名空间、虚拟接口、私有子网和端口映射。

14.1 容器有自己的网络视角

在常见Linux Docker桥接网络中，容器会看到自己的网卡、IP、路由表和DNS。对容器内部的程序来说，它像一台独立主机。

图14-1　Docker桥接网络（简化）

↔
docker bridge172.18.0.1

网络命名空间像同一栋楼里各自独立编号的房间：每个房间都有自己的“这里”和“出口”。容器里的localhost说的是当前这个网络空间，宿主机里的localhost说的是宿主机那个空间。先确定命令在哪一侧执行，再解释地址，能避开很多容器连接错误。

14.2 容器里的127.0.0.1指谁

在这里假设的独立网络命名空间中，它指当前容器的回环接口。使用host网络模式或共享网络命名空间时，情况不同，不能一概套用。假设数据库运行在宿主机127.0.0.1:5432，容器里访问127.0.0.1:5432是在找“容器自身的5432”，通常找不到宿主机数据库。

14.3 为什么Web程序在容器里常要监听0.0.0.0

如果Web进程只监听容器内127.0.0.1:80，通过容器网卡进来的连接到不了它。监听0.0.0.0:80通常意味着同时接受容器各IPv4接口上的连接，再配合Docker发布端口。

14.4 -p 8080:80究竟做了什么

Docker官方文档把它定义为把宿主机8080映射到容器TCP 80：

→

→

如果不指定宿主机IP，Docker默认可能发布到宿主机所有地址，因此存在对外暴露风险。只想让宿主机本机访问时，可显式绑定回环：

docker run -d --name netbook-local -p 127.0.0.1:8081:80 nginx:stable-alpine

以上说明针对常见bridge网络的默认NAT模式。Docker官方文档提示：28.0.0之前的版本存在同一二层网络访问回环发布端口的历史问题，应升级并核对网络配置。第二个示例使用8081，避免与前一个示例冲突。

14.5 EXPOSE和publish不是一回事

镜像里的EXPOSE 80主要表达“容器应用预期使用80端口”的元数据/约定；它不会自动把端口发布到宿主机公网。真正对外发布通常由-p/--publish、Compose ports等配置完成。

14.6 容器之间怎样互相访问

同一个用户自定义bridge网络里的容器，可以直接通过容器网络通信，Docker还提供容器名级别的DNS解析。不要把宿主机映射端口当成容器间通信的唯一方式。

14.7 一个可复现的Compose网络实验

先安装Docker Engine与Compose插件，或Docker Desktop。把下列内容保存为compose.yaml，在同目录的.env中设置POSTGRES_PASSWORD=你自己生成的强密码，再执行docker compose up -d。首次启动需要联网拉取镜像，宿主机8080端口须空闲。

services:
  web:
    image: nginx:stable-alpine
    ports:
      - "127.0.0.1:8080:80"
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: netbook
      POSTGRES_DB: netbook
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?请在.env中设置数据库密码}
    volumes:
      - db-data:/var/lib/postgresql/data
    # 不发布5432到宿主机；同网络服务可用db:5432访问
volumes:
  db-data:

访问http://127.0.0.1:8080可看到Nginx默认页。执行docker compose exec db pg_isready -U netbook -d netbook检查数据库，执行docker compose exec web nslookup db观察服务名解析。两个服务共享Compose默认网络；Nginx尚未连接数据库，这个实验只验证端口发布与服务发现。停止实验用docker compose down，命名卷中的数据库数据会保留。

安全设计：未发布数据库端口不等于完全隔离：同一容器网络中的服务仍可能访问数据库。生产环境还需分网、认证和最小权限，镜像应固定到经过验证的版本或摘要。

14.8 读懂实验结果，再整理实验环境

运行Compose前，先停止前面名为netbook-web的独立示例容器，或跳过那个示例，避免它占用8080。docker ps用于查看正在运行的容器；只有确认属于自己这次实验的容器，才执行后面的停止或删除操作。Compose命令应在examples目录或你保存配置的目录里运行。

正确的对照是：宿主机浏览器访问127.0.0.1:8080看到Nginx页；容器内部查询db得到容器网络地址；数据库就绪检查出现accepting connections等成功提示。首次初始化可能需要等待后重试。服务名db对应的内部IP可能变化，应用应优先使用服务名，不要把当前IP写死。

本示例没有发布宿主机5432。即使容器内数据库正常，宿主机访问127.0.0.1:5432也不能据此访问到它；若该地址能连通，还要确认是否碰巧是另一套本机数据库。

# 在Compose配置所在目录停止该实验；保留命名卷

第15课　云网络、CDN与负载均衡：把一台服务器扩展成一个系统

云网络的核心并没有推翻前面的知识。VPC仍是IP网络，安全组仍是访问控制，负载均衡仍在转发连接或请求，NAT网关仍在做地址转换。

15.1 VPC是什么

VPC可以理解为云厂商给你的一个逻辑隔离网络。你规划CIDR，例如10.20.0.0/16，再划多个子网：

图15-1　一个典型云VPC

→

“公网子网”并不意味着其中每台机器天然拥有公网IP；一般还取决于路由、互联网网关、公网地址分配和安全策略。

VPC像云端一块由你规划的园区，子网像园区里的几个区域，路由表告诉数据从哪条出口走，安全组规定哪些通信可以通过。把名字改成“公网子网”不会自动接通公网，就像给房间贴上“出口”标签，也不会自动修出一扇门。各家云平台的产品细节不同，要以实际配置为准。

15.2 弹性公网IP为什么有用

普通云主机的公网地址可能和实例生命周期绑定。弹性公网IP一类产品把公网地址作为独立资源，让你可以重新绑定到不同实例，降低服务迁移时地址变化的影响。

15.3 NAT网关解决什么

很多服务器只需要“主动访问互联网下载更新、调用API”，不需要“被互联网主动访问”。把它们放在私有子网，再通过NAT网关出站，可以减少公网暴露。

负载均衡像统一接待台分配空闲窗口；健康检查则是定时确认窗口还能办事。健康检查必须选对端口、路径和成功条件：某台机器能回一个“正常”，不代表登录、支付等完整业务都正常。一个后端坏了，能否避开它，取决于检查与转发配置。

15.5 CDN与源站

CDN在全球/区域部署边缘节点。用户通常先访问附近边缘；静态资源若缓存命中，可直接返回；动态请求或未缓存内容则回源。CDN还常集成TLS终止、WAF、DDoS缓解、边缘计算等能力。

第16课　互联网骨干、AS与BGP：全球没有“总路由器”

前面讲的是一台设备怎样把包交给默认网关。现在把视角拉到全球：不同运营商和大型网络之间，怎样知道“这个IP前缀该往哪边走”？

16.1 AS是什么

AS（Autonomous System，自治系统）可以粗略理解为在统一路由策略下运营的一组网络。运营商、云厂商、大型内容网络、高校研究网等都可能拥有ASN。

⇄

⇄

16.2 BGP解决什么

BGP是自治系统之间交换可达性信息的核心协议。一个网络会告诉邻居：“这些IP前缀可以通过我到达”，并携带路径属性。邻居根据策略选择路由，再继续传播。

因此BGP并不是“每个数据包都问一次”。路由器先通过BGP等协议形成路由表/转发表，然后实际数据包按转发表高速转发。

把互联网看成几家运输公司互相交接货物。BGP交换的像“哪些地区经由我能到、沿途经过哪些公司”的线路信息，实际数据包像货物。路线会受到合作协议、费用和策略影响，不能只用地图上的直线距离判断哪条路径一定被选中。

16.3 为什么互联网路由不是简单选最短距离

BGP首先是策略型协议。商业关系、对等互联、出口成本、流量工程、安全策略都会影响路径。AS_PATH长度只是常见决策因素之一，不等于地理距离。

16.4 Transit与Peering

Transit一方购买另一方的互联网转接能力，让流量到达更广泛的互联网。
Peering两个网络直接互联交换彼此及约定范围内的流量，常见于IX或私有互联。

16.5 IX是什么

Internet Exchange（互联网交换中心）给多个网络提供高效互联场所。两个网络如果能在本地直接交换流量，就可能减少绕路、成本和延迟。

16.6 为什么BGP安全很重要

错误路由宣告可能让流量走错路甚至造成大范围不可达。现代互联网逐步采用RPKI等机制帮助验证“某个AS是否被授权宣告这个IP前缀”。常见RPKI路由起源验证（ROV）检查前缀与起源AS的授权关系，并不验证整条AS_PATH，也不保证路径性能或数据机密性。

16.7 traceroute看到的是BGP路径吗

不完全是。traceroute展示的是探测包在IP层遇到的一系列可见跳点；BGP描述的是AS间前缀可达性和策略路径。一个AS内部可能有很多跳，有些路由器也不回应探测，所以两者不能简单一一对应。

16.8 入门阶段：会看路径，也会说明看不到什么

运行本课或第12课的tracert/traceroute时，先关注第一跳是否是本地出口、后面是否继续有响应、终点能否访问。一个AS内部可以经过很多路由器，所以探测的“跳数”不能直接当成经过了多少个运营商。路径也可能因探测协议、负载均衡和时间而变化。

你不需要在家用路由器上配置BGP才能完成入门任务。当前要能解释：DNS负责把名字查成记录，IP路由负责逐跳转发，BGP帮助独立网络交换前缀可达信息。三个系统有联系，各自解决的问题不同。

小测：查到两条AS路径，一条经过两个AS、一条经过三个AS，前者就一定更快吗？
不一定。AS数量不等于地理距离、链路质量或业务延迟；策略、拥塞、互联容量和服务位置也影响体验。实际速度需用真实业务与性能测试验证。

实用的网络能力体现在排错时能有依据地判断：问题发生在链路、地址、路由、DNS、端口、TLS还是应用？

17.1 一套通用排错顺序

图17-1　从近到远、从底到高
① 链路网线/Wi-Fi
→
② 地址IP/掩码/DHCP
→
③ 网关/路由
→
④ DNS
→
⑤ 端口/TCP
→
⑥ TLS/HTTP/应用

先问清楚故障范围：一台设备还是所有设备？一个网站还是所有网站？有线正常而无线异常吗？刚改过哪一项？这些问题像医生先问症状，能快速缩小检查范围。每次只改一个变量，记下改动和结果，没改善就恢复，避免把一个小问题改成几个新问题。

17.2 场景一：完全上不了网

  1. 确认网线/无线已连接。
  2. 查看IP，是否拿到了合理地址；如果是169.254.x.x，重点查DHCP/接入。
  3. ping默认网关。
  4. ping一个已知公网IP，区分“互联网路由”和“DNS”。
  5. 再查域名解析。
ping只验证特定ICMP探测。不回应可能是ICMP被过滤或限速，不能直接判定网络中断；ping成功也不证明TCP 443、TLS和HTTP正常。结合端口测试与实际请求判断，双栈环境还要分别检查IPv4与IPv6。

17.3 场景二：能ping IP，域名打不开

优先看DNS：

nslookup example.com
# 或
dig example.com

如果解析失败，检查DNS服务器、DoH/DoT设置、企业策略和本地hosts文件。

17.4 场景三：域名能解析，但443连不上

此时DNS已经不是第一嫌疑。继续测试目标端口：

# Linux/macOS
nc -vz example.com 443

# Windows PowerShell
Test-NetConnection example.com -Port 443

若TCP 443可连，再用curl -v查看TLS和HTTP阶段。TCP端口测试无法证明UDP 443正常；使用HTTP/3时，应另查QUIC连接或浏览器协议列。

17.5 场景四：127.0.0.1能打开，局域网IP打不开

先检查程序监听地址：

# Linux
ss -lntp

# 看是 127.0.0.1:8080 还是 0.0.0.0:8080 / 192.168.1.x:8080

如果只监听回环，改应用绑定地址。若已监听外部接口，再查主机防火墙。

17.6 场景五：服务器本机能访问，公网打不开

按顺序查：

  1. 应用是否监听正确接口。
  2. 主机防火墙是否放行。
  3. 云安全组/网络ACL是否放行。
  4. 服务器是否真的有公网可达IP。
  5. 家庭环境是否有端口映射、CGNAT。
  6. 运营商是否限制入站端口。

17.7 场景六：偶尔很慢，不是完全断

这类问题最难，重点收集指标：RTT、丢包、抖动、路径、CPU、连接数、DNS耗时、TLS耗时、TTFB、下载吞吐。TTFB常用来观察从发起请求到收到首个响应字节的等待，具体计时边界以工具为准；它可能包含网络和服务器处理时间，不能直接当成纯网络延迟。不要只截一张测速图。

17.8 tcpdump/Wireshark什么时候上场

当你已经知道大概哪一段有问题，但还不清楚具体报文发生了什么，就抓包。例如：

# Linux：抓TCP 443
sudo tcpdump -i any tcp port 443

# 抓DNS
sudo tcpdump -i any port 53

Wireshark可观察连接、重传和可见的协议元数据。HTTPS下的HTTP/1.1、HTTP/2，以及HTTP/3的应用内容都受加密保护，不能凭普通抓包直接读取。分析应用内容通常需要端点提供会话密钥并由工具支持解密；DoH、DoT和ECH也会改变可见范围。

排错黄金规则：先证明哪一层是好的，再向下一层推进。每一步都要有证据，不要“一打不开网页就改DNS”“一延迟高就怪运营商”。

17.9 把“打不开”改成别人能复核的问题

试着用五句话描述故障：“哪台设备、什么时间、访问哪个目标、看到什么错误、已经验证了什么”。例如：“笔记本Wi-Fi连接正常，能打开路由器页面；查询目标域名有A记录；TCP 443测试失败；同一手机用蜂窝网络访问正常。”这个例子把范围缩小到某条路径或访问条件，但还不能单凭这些证据判定是哪家运营商的问题。

排错记录模板（填写用，不执行）：
时间与设备：
目标与具体错误：
本地IP / 前缀 / 网关 / DNS：

仍未验证的部分：

常见结果要分开读：连接被拒绝常见于目标主动拒绝或没有服务监听，也可能由中间设备返回；超时只说明在时限内没等到预期结果；证书错误要查名称、信任、有效期及系统时间；404要查资源路径；502要查代理与上游。每种现象都比“坏了”更有用。

排错小题：域名能解析、TCP 443能连接、curl提示证书名称不匹配。现在优先做什么？
确认访问的主机名、实际入口与证书声明的名称，检查是否配置错站点、证书或代理。DNS和TCP已有部分成功证据，不应把关闭防火墙或跳过证书验证作为默认处理方式。

第18课　综合实战：从看懂到亲手跑通

现在假设你在家里打开笔记本，连接Wi-Fi，然后输入https://www.example.com/。从按下回车到页面出现，发生了什么？

阅读这个流程时：下面以一次普通的新访问说明主线。真实浏览器可能复用现有连接、命中缓存、使用代理，步骤也可能并行；IPv6通常不需要家庭IPv4式NAT。图示帮助你把知识连起来，不代表每次打开网页都会原样重走全部步骤。

18.1 第一步：设备先加入本地网络

Wi-Fi完成无线接入与安全认证。之后DHCP通常给电脑分配IPv4地址、前缀/掩码、默认网关和DNS；IPv6通常通过RA发现默认路由，地址可由SLAAC生成或由DHCPv6分配，DNS参数也可能从RA或DHCPv6取得。

18.2 第二步：浏览器解析URL

浏览器知道：

协议：https
主机：www.example.com
默认端口：443
路径：/

18.3 第三步：DNS把名字解析成地址

系统/浏览器先查缓存，再向递归解析器查询A、AAAA等记录。递归解析器必要时从根、TLD一路找到权威DNS。

18.4 第四步：操作系统决定从哪里发出去

目标IP通常不在家庭192.168.1.0/24里，于是匹配默认路由，把下一跳交给家庭路由器。

18.5 第五步：找到默认网关的链路层地址

IPv4以太网环境里，电脑通过ARP找到网关MAC，把IP包装进以太网帧或无线链路帧送给AP/路由器。

18.6 第六步：家庭路由器做NAT

若使用IPv4私网，路由器把192.168.1.23:临时端口转换成WAN侧地址和端口，并记住映射。若运营商使用CGNAT，外面可能再做一次转换。

18.7 第七步：互联网逐跳路由

运营商路由器根据目标前缀查表转发。跨AS的可达信息主要通过BGP形成。包可能经过多个运营商、交换中心、骨干网络，最后进入网站或CDN所在网络。

18.8 第八步：建立安全连接

如果使用HTTP/2，通常先建立TCP，再进行TLS握手；如果使用HTTP/3，则建立QUIC连接，TLS 1.3握手被集成进QUIC的连接建立流程。客户端验证服务器证书与域名。

18.9 第九步：发送HTTP请求

浏览器发送类似“我要/这个资源”的请求，服务器/CDN返回状态码、响应头和HTML。

18.10 第十步：浏览器继续请求几十甚至几百个资源

HTML里可能引用CSS、JavaScript、图片、字体和API。HTTP/2/3会复用连接并发交换数据，CDN可能直接在边缘返回大量静态资源。

18.11 第十一步：页面渲染

浏览器解析HTML/CSS、执行JavaScript、布局和绘制。到这一步，慢不一定是网络：前端代码、CPU、GPU、第三方脚本也可能成为瓶颈。

18.12 学完后你应该能回答这些问题

为什么127.0.0.1只能访问自己？因为它属于回环地址块，语义就是当前主机内部。
为什么0.0.0.0常出现在服务监听配置？它作为未指定地址，API常用来表达“绑定全部本机IPv4接口”。
为什么家庭端口映射做了还不通？可能被CGNAT、上游NAT、防火墙、运营商策略或应用监听范围阻断。
为什么HTTPS不等于HTTP/2？HTTPS描述安全使用HTTP；HTTP/1.1、2、3是HTTP的版本/映射方式。
为什么HTTP/3用UDP还可以可靠？可靠性由QUIC自己在UDP之上实现。
为什么域名不是服务器？域名是名字；DNS可把它指向IP、别名、CDN等服务入口。
真正入门的标志：遇到网络问题时，你脑中已经不再只有“网络坏了”四个字，而能把它拆成：本地链路、IP配置、网关、路由、NAT、DNS、传输连接、TLS、HTTP和应用。

18.13 实操一：把自己的第一个网页跑起来

先区分两个角色：浏览器是提出请求的客户端，下面启动的程序是接收请求的服务器。它们可以运行在同一台电脑上。这个实验只用本机回环地址，帮助你亲眼看到URL、端口、HTTP响应和服务进程之间的关系。

  1. 准备：确认Python 3可用；不确定时回到动手准备。在项目文件夹打开终端，确认里面有examples目录。实验使用8000端口，与教程预览的4173端口分开。
  2. 启动：运行下方命令，然后让这个终端保持打开。看到Serving HTTP on 127.0.0.1 port 8000一类提示，表示程序已开始等待连接。
  3. 访问：在同一台电脑浏览器输入http://127.0.0.1:8000/，应看到“我的第一个网络实验”。打开页面里的“查看状态文件”，应显示network-lab: ready。
  4. 观察：刷新页面，终端应出现GET请求日志；浏览器Network面板应显示文档与状态文件的请求。你已经让客户端和服务器真正交换了HTTP数据。
python -m http.server 8000 --bind 127.0.0.1 --directory examples/lab-site

如果提示地址已被占用，不要随意结束陌生进程；换成8001，并把后面所有实验URL和端口测试中的8000一起替换。若提示找不到Python，按准备部分换命令名称或先完成安装。若显示目录列表、404或空白页，先核对启动目录、--directory路径和文件是否齐全。

为何指定目录和地址？本实验只提供examples/lab-site里的公开演示文件，避免把其他个人文件作为目录内容展示；绑定127.0.0.1使服务仅供本机访问。Python的简易HTTP服务适合学习和临时测试，不用于生产部署。

18.14 实操二：制造两个小故障，练习分层判断

先保留服务运行，在浏览器访问http://127.0.0.1:8000/not-here.html。应收到404：地址和端口已经通了，但这个文件不存在。回到正确路径又能打开，说明路径也是请求的一部分。

接着在第二个终端测试TCP端口，再查看HTTP响应头。复制自己操作系统对应的两条即可；Windows这里明确使用curl.exe，避免旧版PowerShell中同名别名的差异。

# Windows PowerShell
Test-NetConnection 127.0.0.1 -Port 8000
curl.exe -I http://127.0.0.1:8000/

# macOS / Linux（需有nc和curl）
nc -vz 127.0.0.1 8000
curl -I http://127.0.0.1:8000/

服务运行时，Windows的TcpTestSucceeded应为True，nc通常提示连接成功，curl应看到200状态的响应头；HTTP版本字样与头部细节以实际输出为准。-I请求响应头，用来快速观察HTTP结果；它不下载正文。

现在回到启动服务的终端，按Ctrl+C停止，再重复端口测试和curl。常见结果是连接被拒绝，或在当前环境中等待后失败。它与前面的404不同：这时连HTTP响应都没有拿到。浏览器可能缓存旧页面，判断停服效果优先看新的命令结果。随后重新运行启动命令，确认恢复。

解释题：为什么ping 127.0.0.1仍可能成功，8000端口却打不开？
ping测试的是回环上的ICMP探测，不要求8000端口有Web服务。网络接口能回应与应用进程正在监听是两个条件。

18.15 实操三：整理自己的网络证据

  1. 用第2课的方法记录活动接口、IP、前缀、网关和DNS；说明每项分别干什么。
  2. 查路由表，指出本地直连网段与默认路由；用自己的两个目标示例解释直连和经网关的差别。
  3. 运行nslookup example.com，区分解析器地址与查询结果；说明这项成功不能证明HTTPS已经成功。
  4. 选择一个自己能访问的HTTPS站点，用浏览器Network面板记录URL、状态码和协议；观察失败时停在哪个阶段，不要求网站一定支持HTTP/3。
  5. 把结果写入排错记录模板，每条结论都注明它依据的观察。

没有某个命令时，可以先用系统网络设置与浏览器获取相同类别的信息，并在笔记中注明工具限制。基础能力重在能解释证据，不在于背下所有命令参数。

18.16 可选实操：让同一局域网的另一台设备访问

需要第二台设备和可信的家庭实验网络。先停止回环服务，从第2课记录中找到电脑当前的局域网IPv4。若实际为192.168.1.23，可按下方启动；地址不同必须替换。只在自己可管理的实验网络中进行，不在公共热点、办公受管网络或公网接口上照做。

# 192.168.1.23必须换成实验电脑当前的真实局域网IPv4
python -m http.server 8000 --bind 192.168.1.23 --directory examples/lab-site

先在实验电脑打开http://真实局域网IP:8000/，再让同一家庭网络中的手机打开相同URL。手机这里不能写127.0.0.1，那会指向手机自己。若出现系统防火墙询问，只按本课的受限访问需求设置，并记录临时规则，以便实验后撤销；不关闭整个防火墙。

电脑自己能开、手机不能开时，依次检查真实地址、监听地址、两台设备的接入网络、访客/AP隔离和防火墙。暂时无法调整受管规则时，记下限制即可，不把现象误判成HTTP协议失效。成功后回看日志，找到手机来源地址，再按Ctrl+C停止服务并撤销临时规则。
